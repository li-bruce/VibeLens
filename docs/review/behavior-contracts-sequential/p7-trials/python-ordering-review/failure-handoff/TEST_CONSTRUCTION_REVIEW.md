# Existing test boundaries and proposed correction for review

This is a source review and a candidate test plan. No application, existing test, expected business result, capacity or deadline has been changed. No recording retry or post-verify has run. The first repair23 failed recording and the earlier repair22 failure remain original evidence.

The first repair23 recording established request -> start -> complete -> revoke, native journal sequences 119 -> 120 -> 121 -> 122 for the same job/file/Bob grant. It did not establish revoke -> admission. The final ready state is correct. The unmodified script's initial queued SQL read is an observation at that instant, not a lock or synchronization point preventing the default worker from claiming immediately afterwards.

For a deterministic revoke-before-admission test, reuse the existing controlled browser/native fixture: enqueue through the real route with no automatic worker started; await the actual revoke response; independently verify matching grant inactive/new revision and job still queued; only then call the existing `Service.start_preparation()`. Require native journal request < revoke < reject, same job/file/Bob identity, denied current permission, no admission/result, and the original terminal/re-share/new-request assertions. The synchronization consists of completed real business transactions followed by the next native operation. This is already the construction in `tooling/browser_acceptance.py:97-119` and `tests/test_business.py:83`; explicit journal joins can make that proof reviewable if the proposed change is approved.

The complementary controlled case remains start -> revoke -> complete, with admission committed before the revoke, actual ZIP collection twice, and exact SQL/frame checks. It already exists at `tests/test_business.py:143` and `tooling/browser_acceptance.py:119-132`. The eight existing cancel/start races retain the current winner-based rule and all their native effects; observing one winner in all eight does not claim coverage of both race outcomes.

For an ordinary normal-entry recording, retain separate unchanged `run.py` and `bo.py serve`, default worker, capture-all, 2048 capacity, original transport/Stop deadlines and the 20000 ms UI bound. Issue normal business operations and determine the valid result from the independent committed journal for that same attempt and matching grant. Revoke-before-admission requires rejection with allowed=false and no result. Admission-before-revoke permits completing the admitted attempt. A mismatching result or a missing outcome within the existing bound fails. Do not depend on mouse speed, sleeps, polling alignment, a stopped worker, direct SQL mutation, method wrappers, mocked completions or retry-until-a-chosen-order.

The evidence allocation in rows 5, 8 and 14 is a review decision for the main chat before any test edit: ordinary scheduling cannot guarantee both ordering branches, and its record must not be labelled twenty-of-twenty if a required branch-specific observation did not occur. The controlled case supplies the deterministic rule proof in its own clearly labelled evidence. If all twenty literal observations are required in one default-worker recording, the current public interfaces do not provide an admission barrier to guarantee that requirement; merely clicking faster or increasing waits will not supply it.

After review, any authorized implementation would use a new explicit attempt/evidence namespace, retain these failures, preserve every protected native/negative/concurrent/browser case, and run the full native gate, ordinary complete recording and post-verify before independent main UI or accept. At present this document is only a proposal, and all dependent execution remains stopped.
