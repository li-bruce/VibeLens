## 七项修改

| 问题 | 修改结果 |
| --- | --- |
| 图标与层颜色不一致 | 九层各用一种颜色，二维图标、三维对象、区域和层工具共用；形状仍区分节点类型。 |
| 节点密集、跨组连线杂乱 | ELK 先排列层与类型分组，D3 再排列组内完整子树；对外连接多的节点靠近相邻分组。二维和三维共用初始平面坐标。 |
| 文件结构层为空 | 文件、目录、导入、导出和包依赖独立扫描；查看文件结构不再依赖打开完整函数分析。新录制保存当时的文件结构，各视图独立保存层显隐。 |
| 时间轴区间太短、状态重叠、横向连接不清楚 | 按实际实例区分状态；并行区间在同一层行内错开；短调用有可选择的最小宽度，保留实际耗时；横向连接带弯钩和箭头。 |
| 层顺序与颜色混乱 | 默认顺序为业务 → 状态 → 规则 → API → 函数与值 → 工程结构 → 代码符号 → 数据操作 → 数据结构。已有明确自定义顺序保留。 |
| 录制步骤不易分辨 | 按真实父子调用缩进，按层着色；事件 ID、顺序和原始内容保持。 |
| 三维节点小、线条抢眼 | 放大立体对象并保留最小屏幕尺寸；普通连线变细、半透明，选中与运行中的关系更突出。 |

已有手动位置和固定节点继续保留。打开旧视图后，可点 **重新排列（Arrange）** 使用新布局。

## 录制停止问题

实际多用户操作还发现了采集端的积压。已修复队列停止边界、事件接收与保存互相阻塞、逐条日志写入，以及录制列表和检查点反复扫描文件树的问题。字段、身份、源码一致性、丢失提示和原有容量、超时检查均保留。

开始录制时保存静态结构；检查点读取运行事实；录制目录和版本查询读取图版本。项目原有的无参 `view()` 扩展仍然生效。开始录制期间若源码发生变化，直接拒绝开始。

失败轮次、原始录制、修复和复测分别保留在此目录。最终结果见 [完整修复报告](README.md)。

- 文件共享项目完成上传、审核、延迟通知、共享、下载与撤销；实际 HTTP 响应逐项对照记录。三个人的网页持续刷新时停止录制，保留 15,278 条事件，18 条受检响应各有唯一采集记录，未报告丢失或采集错误。
- 九层来源逐项核对：文件与代码结构来自源码，数据库结构来自实际结构，运行状态来自 11 个原生状态快照。没有缺失的已映射文件或观察到却找不到节点的状态值。
- 九个视图分别检查实际画布；文件树展开后有 21 个文件、36 条关系，数据结构展开后有 24 条关系。旧概览中的隐藏设置不会再清空其他预设，单独隐藏某层后刷新页面也会保留。
- 独立项目增加文件重命名后，再检查九层的内容、源码版本和关联；保留首次映射检查失败、补齐映射和再次通过的材料。
- 六个核心定义/引擎文件、JavaScript 原执行器、试用项目的 75 个受保护文件和 244 个原节点 ID 均未改变。

## 已完成的针对性检查

- 原生 SQLite 与 OpenTelemetry：业务等待区间、嵌套调用、区间中途开始录制、拖拽定位、缩放及二维/三维游标一致。
- 两个真实并发执行：每组按层组织、独立收起、跨组资源连接、横向连接及四种连线形式。
- 2 万事件：绘制 P95 24.2 ms，定位 P95 73.9 ms；4 千节点、1.6 万条边：渲染 P95 20.8 ms，9 次绘制调用。数值来自本机自动化测试。
- 14 项录制边界、11 项事件批次、3 项日志轮转与数据隔离，以及旧录制兼容、文件依赖和源码关系检查。
- 126 个 Python 模块与 94 个 JavaScript 模块的语法、检查和排版通过。

短函数仍按实际调用耗时显示。跨异步任务持续存在的业务活动，需要有真实的生命周期注册；页面不会把函数的瞬间调用自行延长为业务等待。
