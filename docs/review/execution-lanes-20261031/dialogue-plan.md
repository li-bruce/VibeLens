# Fresh dialogue trial

Start only after the shared fixes and repository checks pass. Use a new application
directory and a new Codex conversation. Maintained Skill sources are read-only to
the trial developer. Keep the actual public questions and replies.

## Initial simulated user request

> 我要做一个小团队的文件共享网页。上传后交给同事审核，审核通过才能分享给指定的人，文件只能登录后访问。先在本机用 Python 和 SQLite 跑起来，我想用 VibeLens 看里面怎么运转。

Answer the developer's actual questions as the prospective user. Use ordinary
Chinese, make reasonable small-team choices, and confirm the displayed graph only
after reviewing it. Do not supply a scripted questionnaire or undisclosed expected
answer. Keep source and identifiers in English.

## Ordinary iterations

After v1 genuinely works, ask for withdrawing a pending submission. Then ask for a
small change to the review result shown to the uploader, adapting to the existing
confirmed behavior. Do not remind the developer about probes, graph synchronization,
recall or verification in these business requests.

## Independent inspection

- Verify the confirmed business graph, shared rule graph, native state declaration,
  API handlers, functions/values, data operations, project tree, code and data model.
- Inspect actual entered/returned/error calls and selected values against native
  HTTP/storage observations. Check normal and denied/error paths separately.
- Inspect each iteration for new files/functions/fields, persistent contracts,
  recall, automatic source scans and accepted current builds.
- Exercise viewer recording, live inspection, one-row-per-layer bands, per-group
  collapse, causal links, graph/timeline cursor, 2D/3D routes and view persistence.
- Keep framework/Skill/viewer defects separate from application defects. Repair
  general defects in the maintained project before another fresh trial.

All business answers are simulated trial evidence, not production requirements
confirmed by the human owner of VibeLens.

## Retest sequence

1. Trial 01 stopped at discovery after exposing the shared caption defect.
2. Trial 02 built the application from scratch. Its first complete gate passed
   business/state/project checks and failed mapping at the shared data-exit defect.
3. Trial 03 starts a new conversation and directory, reuses the frozen business
   source candidate and confirmed requirements, installs the corrected runtime,
   and creates new data, project identity and observation baseline. It then makes
   ordinary feature iterations. Reusing source is explicit adoption evidence,
   not another from-scratch generation result.
4. Trial 03 stopped at its confirmed design because low-zoom captions vanished.
   The shared renderer repair was verified before trial 04 resumed the same
   prepared project in a fresh conversation. Trial 04 passed all four runtime
   categories and actual upload/review/share/download, but stopped before accept
   because data adapter events had no enclosing call parent.
5. After repairing shared parent-context propagation and its native regressions,
   a new conversation resumes the frozen app through its latest review handoff.
   It performs fresh checks over fresh events, finishes Web acceptance and then
   receives ordinary business iterations. Earlier recordings are never patched
   or counted as new acceptance.
