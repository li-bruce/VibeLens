## 这轮解决什么

将最近五轮讨论收束为一条完整路线：用户确认意图，AI 补齐实现事实，统一 JSON 保存定义与约束，每轮开发更新代码、图和证据，最后分别报告映射情况、业务结果和所选模型的验证结果。

已有的业务网、状态网、规则网、多模型注册、源码扫描、运行采集和每轮回忆继续复用。重点补足“哪些内容必须定义、由谁回答、依据是什么、变化后哪些证据失效”。

**问答要形成可确认、可绑定和可验证的项目模型。** 建模产物包括多个业务网络、多个对象的状态模型、具有共享条件的规则网络，以及它们之间的实际联系。角色适配服务于这些建模任务，决定表达方式和参与深度。

这里沿用用户的“森林”说法表示多个模型或子网。业务和状态可以循环，规则可以共享依赖；不会把这些结构强制改成树，也不会为了画成一张连通图而增加关系。

| 核对内容 | 当前工程基础 | 本轮计划补足 |
|---|---|---|
| 业务森林 | `discovery.networks` 保存多个业务网，存在行为关系与连通性检查 | 从已描述能力整理模型总览，区分独立业务与遗漏关系，逐网确认触发、分支和结果 |
| 状态森林 | `state_models` 与原生 `model.machines` 注册、绑定多个模型 | 引导确认状态属于哪个对象、实例如何区分，以及事件、条件、效果和适用的并发等待 |
| 规则森林 | 一个共享表达式注册表，多个操作根及依赖子网 | 逐项确认事实、组合条件、参数绑定、复用范围和读取时点；保持共享节点身份 |
| 跨网联系 | 业务到事件、转换到规则、规则到事实等有类型的引用 | 补齐相关的消息交接、共享资源、顺序与完成边界，并形成真实采集要求 |
| 引导与确认 | 已有问题记录、每轮筛选、语义快照和历史 | 先识别建模任务与缺口，再生成问题；按模型分组查看和修改，保存实际审阅范围 |

完整源码依据、模块复用位置、协议补充及验收要求见[专项核对](model-construction.md)。没有源码的初期也能构建模型；新增源码发现的能力在后续进入同一套模型核对流程。

| 讨论内容 | 本轮方案 |
|---|---|
| 软件能否完整描述 | 明确对象、变量、操作、实例、消息、资源、外部输入与版本；区分实际运行边界和分析时的有限范围 |
| 用户与 AI 分别承担什么 | 用户确认业务含义；AI 根据源码与测试回答实现问题；工具验证格式、引用、运行事实和结果 |
| 问题太多如何处理 | 按问题类型、负责人、阶段、依赖、影响范围和阻塞程度分配；每轮只问当前需要人回答的少量问题 |
| 是否先了解回答者定位 | 简短询问参与方式；将知识背景、决策权限、希望参与的深度分开保存，可跳过、可调整 |
| 借鉴 TLA+ | 引入初始条件、动作前后变化、持续成立的要求、进展要求、环境假设与实现对应关系；后续选配 TLC |

## 用户会经历什么

1. 用户描述应用。VibeLens 整理模型总览，展示已提到的业务能力、状态所属对象、规则及独立或共享关系。
2. 必要时了解参与偏好，例如“主要确认业务”“一起讨论实现”“按需看技术细节”。职位仅供表达方式参考，不能代替授权。
3. 按当前模型需要形成的定义识别缺口，提出有来源、会影响模型的问题。实现细节由 coding AI 查源码、确定方案、补证据。
4. 逐网展示业务路线、对象状态转换、共享规则依赖以及跨网边界，并给出实际可打开的 Web 地址。问题较多时按模型分组，支持回看、修改和继续；用户在对话里确认当前含义。
5. AI 开发时自动维护声明、参数、函数绑定、探针和测试。用户继续关注自己的项目。
6. 每轮结束，用户看到更新后的图，以及哪些检查通过、哪里缺少观察、哪里存在业务问题。
7. 项目需要时，对指定模型和边界运行有限分析。发现的推演路径可以在图中查看，再转成真实程序的回归场景。

问题数量不设“总共三问”的限制。每轮最多显示少量就绪问题，尚不影响当前工作的内容延后处理。已有明确答案直接复用。反例用于澄清含义或检查已确认要求，不自动增加新的业务政策。

## AI 每轮要做什么

| 时点 | 固定工作 | 可检查产物 |
|---|---|---|
| 开始 | 读取当前确认、模型清单、开放问题、源码范围、框架边界及失效证据 | 简短回忆报告、当前变更记录 |
| 修改前 | 找到受影响子网和跨网依赖，确认是否改变业务含义 | 局部变化图、实现与验收要求 |
| 开发中 | 编写原生逻辑、独立状态模块、说明性注释、隔离的采集接线 | 源码绑定、读取/写入/完成依据、运行事件 |
| 开发后 | 从源码独立扫描新增、修改和删除内容，修复遗漏 | 映射差异、逐层观察要求 |
| 验收 | 执行原有检查及新增行为检查，保留失败和复测记录 | 各维度结果、精确版本、未覆盖项 |
| 接受 | 仅接受当前候选的有效证据，保留用户布局与批注 | 新基线、更新后的图 |

文件化要求不能自行唤醒任意 AI 系统。支持钩子的宿主负责调用；其他宿主由 Skill 明确要求执行。漏执行时，收尾检查必须报告未完成，不能假装已经自动更新。

## JSON 要补什么

- **行为定义：**对象、变量取值范围、初始条件、操作前后变化、未修改字段、完成时点。
- **模型交互：**共享事实、跨模型事件、队列、资源、等待、汇合、取消和重试的实际语义。
- **检查要求：**哪些条件始终成立，哪些进展依赖什么环境条件，来源于哪条已确认需求。
- **实现对应：**哪个真实值代表哪个概念状态，哪些调用共同完成一个动作，如何独立读取核实。
- **问题记录：**谁回答、何时回答、影响哪里、什么证据有效、何时需要重新检查。
- **建模过程：**尚未形成合法草案的模型目标、应补齐的定义、问题与模型变化的对应、已展示的版本与确认范围。正式定义继续保存在现有模型注册表中。
- **分析配置：**这次分析几个实例、哪些输入和队列边界、支持哪些语义、预算和结果覆盖范围。

定义、绑定、分析配置和结果各有唯一保存位置。分析产物由声明生成，不能再维护一套与项目逐渐分离的模型。现有严格 JSON 校验保留；新字段通过明确版本迁移引入。

## “完整”具体检查什么

| 维度 | 要回答的问题 |
|---|---|
| 描述范围 | 选定业务需要的对象、变量、事件、环境和相互影响是否已经声明？哪些仍未知？ |
| 源码映射 | 从真实源码发现的功能、入口、状态写入和关键调用是否都有对应？ |
| 运行观察 | 实际开始、结束、异常、状态变化和副作用是否被正确采集？ |
| 业务要求 | 已确认的规则和操作序列是否得到满足？ |
| 有限模型 | 指定性质在这次完整探索的有限模型中是否成立？ |

这几个结果分别呈现。映射准确的图可以暴露业务错误；有限模型通过也不代表任意规模的生产程序已被证明正确。生产限制、分析取值上限和抽象转换分别记录。

## 工程实现顺序

| 阶段 | 工作 | 完成标志 |
|---|---|---|
| P0 | 固定兼容基线与回归样本 | 现有模式、多模型和观察机制都有保留检查 |
| P1 | 协议、语义校验、版本迁移 | 错误定义和冲突引用明确失败，旧格式继续可读 |
| P2 | 模型总览、缺口识别、角色适配、逐网问答与确认 | 所需模型及关系已构建，问题指向具体定义，回答和审阅范围可追溯 |
| P3 | 原生绑定与跨模型观察 | Python、Node 的真实参数、消息和提交事实匹配定义 |
| P4 | 每轮自动维护和分项验收 | 新增源码、丢失探针、旧证据复用等问题能被检出 |
| P5 | 图和 Timeline 的渐进查看 | 默认简洁，按需查看条件、依据与缺口；保留布局 |
| P6 | 可选 TLC 接入 | 支持范围明确，反例可定位，超时或不支持不算通过 |
| P7 | 独立对话试用、整理源码、宣传材料 | 失败—修复—复测有证据，介绍与已验证功能一致 |

P1–P5 是基础能力改进，P6 是可选的验证工具。代码按协议、对话、绑定、证据、分析后端和展示分工，避免继续扩大一个总控脚本。函数注释解释输入输出、状态含义和副作用边界；纯格式修改与功能变更分开验证。

新增 A29–A34 验收覆盖：初始多网构建、没有预先写入问题时的建模遗漏、不同角色的等价确认、局部图遗漏和过期确认、模型新增拆分及共享规则迭代、模型到运行和演示材料的一致性。原 A01–A28 保留。

## 宣传页怎样表达

首页继续围绕“看懂 AI 写出的程序”。突出三件事：对话里明确逻辑、运行中逐层追踪、修改后核对变化。多业务网、状态和规则的相互关系通过简洁图示表达。

演示使用一条连贯故事：描述文件共享应用 → 确认业务/状态/规则图 → 录制一次操作 → 发现撤销与排队任务之间的问题 → 下钻核对真实参数和源码 → 通过对话让 AI 修改 → 再次运行验证。具体规则必须先在试用对话确认；发现过程使用保留的真实证据。

Codex 对话只展示开发和改需求。录制、回放、筛选、下钻放在 VibeLens 操作说明中。正式新增功能验收前不修改首页宣传；TLA+ 等技术细节放在技术说明中。演示优先加载预先整理的局部图，完整工具按需打开。

## 后续 AI 从哪里开始

阅读 [agent-guide.md](agent-guide.md)，按 P0 → P1 的顺序开始。该指导文本给出受保护机制、文件归属、执行顺序、检查命令、禁止用假数据通过验收的要求，以及每轮应交付的证据。

当前方案不要求改用一个新的业务框架，也不让观察器接管业务执行。需要补足的是已确认行为到实现、观察和验证之间可以核对的联系。
