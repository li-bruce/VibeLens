## Trial story and dialogue discipline

Use a small file-sharing application with upload, sharing, revocation and queued
downloads. These are enough to exercise business/state/rule models, entrypoints,
source structure, calls/values, storage and asynchronous execution. Keep the first
user request natural and short. The user simulator must not supply all protocol
fields or validation terminology in its opening message.

Keep a separate evaluator note describing the intended business choices. The
coding conversation initially sees only the candidate Skill and the user request.
The simulator responds after each question and may correct a misunderstanding.
Its answers establish trial requirements, not the real user's production policy.

Example response style when the agent asks about queued work:

> 还没开始下载的就不要再开始了。已经在传输的这次可以继续，后面再下载要重新判断。

The agent must translate this into the relevant action/state/rule boundaries and
show the affected graph for confirmation. It must not impose that answer on every
project. Include a second case with a different valid policy to test neutrality.

Run two fresh primary trials: Python drive and Node observe. Reuse existing
automated adapter tests for Python observe and Node drive, extending them for new
semantics. React/Vue fixtures verify frontend/source/entrypoint continuity; do not
claim exhaustive browser application semantics.

Each primary trial includes:

1. Initial request, model inventory, purposeful construction clarifications and
   confirmed business/state/rule network views, including their boundaries.
2. Source-free design, implementation, strict checks and actual live observation.
3. A controlled concurrency scenario and deliberate omission/wrong-value case.
4. Diagnosis of whether the defect belongs to the Skill, framework or application.
5. A semantic iteration confirmed in ordinary language, then graph/code update.
6. A source-only refactor without unnecessary repeated business questions.
7. Full retest after the last framework/Skill repair and preserved screenshots.

Include a small secondary fixture with an explicitly independent capability when
the main sharing story does not naturally contain one. Keep this requirement in the
trial setup; do not teach the Skill to add capabilities to ordinary user projects.
For A29–A34, retain the source statement, modeled interpretation, exact question,
answer, model change and confirmation scope. Assess unnecessary questions and
missing model obligations separately; low question count alone is not success.

Create/message new chats only when the user authorizes those trials. If the host
cannot provide an independent chat or usage counters, disclose that limitation;
do not call a scripted transcript a real independent conversation.

## Per-layer coverage

| View | Static evidence | Runtime evidence / applicable absence |
|---|---|---|
| Business | Confirmed actions, triggers, effects and actual progression/branch relations | Invocation ownership, chosen lifecycle bindings, actual outcomes |
| State | Every applicable model, initial state, events, transitions, guards and hierarchy/activity declarations | Model-qualified state and transition witnesses, wait/resource changes |
| Rules | Shared predicates, arguments, compositions, fact reads and operation bindings | Actual evaluated inputs/results, skipped/unknown/error and read revision |
| Entry points | Method/route or UI/message/command identity and handler bindings | Actual request/callback/message intervals, errors and response facts |
| Project structure | Owned directories/files/modules and containment/import relationships | Structural view only; no fabricated file/folder execution lifetime |
| Code execution | Unique physical declarations, selected values, actual static call references | Concrete calls/returns/exceptions and selected input/output/change facts |
| Storage | Native catalog/model structures with source/provenance | Actual selected reads/writes/commit/rollback; no claim of full row or database-internal lineage |

For each applicable layer record missing nodes, missing edges, stale bindings and
uncollected facts. Hiding a layer or folding a node must not remove its acceptance
obligations. Static existence and runtime execution are checked separately.

## Negative tests and independent expectations

- Keep original expected business outcomes unchanged while mutating an isolated
  implementation. A syntax/startup error is not evidence of semantic sensitivity.
- Mutate AND/OR, guard arguments, permission read time, transition target,
  completion boundary, resource release, invocation owner and probe return.
- Include a model missing an error/environment action. Its smaller state space
  must not be promoted to complete implementation coverage.
- Test exporter defects independently: dropped update, stale-variable read,
  incorrect unchanged set, numeric mismatch and lost action parameters.
- Preserve unknown/partial observations and require the appropriate gap report.
  Derive no causal link or global state from wall-clock proximity alone.
- Confirm that model-level counterexamples remain labeled as such until a separate
  native replay supplies runtime evidence.

## Evidence package

Each trial/release candidate should retain:

```text
docs/review/behavior-contracts-<date>/
  README.md                   # candidate, scope, results and remaining gaps
  dialogue/                   # actual trial messages and graph confirmations
  failures/                   # first failing runs and diagnosis
  repairs/                    # related commits and changed requirements, if any
  final/                      # full final rerun; commands, exits and receipts
  source-and-models/          # pinned definitions, source/build manifests
  runtime/                    # original sanitized records and native assertions
  analysis/                   # generated model/profile, engine result, source map
  screenshots/                # desktop views, drilldown and iteration comparison
```

Record tool versions, OS, producer/build/model IDs, configured scope, property
IDs, assumptions and checksums. Capture screenshots only after the tested state
is reached; filenames and an index tie each image to its step and record.
Archive large logs through the existing review-artifact convention rather than
copying dependencies or private application data into Git.
